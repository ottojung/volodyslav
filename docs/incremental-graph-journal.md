# Incremental graph notification journal

## Goals and non-goals

### Goal 1 — no false negatives

**The journal must have no false negatives with respect to graph changes.** A
graph change is exactly a committed transition in materialization presence,
`ComputedValue`, or the freshness sublevel. The corresponding closed action set
is `add`, `edit`, `delete`, `invalidate`, and `validate`. Every such transition
produces a covering notification. Repeated changes of the same exact action may
collapse and false positives are permitted: this is a possible-change
notification system, not an audit history.

### Goal 2 — bounded O(n) storage

**The total journal size must be O(n), where n is the number of semantic node
keys that exist now or existed historically.** Let `r` be the fixed number of
journal origins in the synchronization domain and `a = 5`. The synchronized
clock is `O(n × r × a)` and local delivery state is `O(n × a)`. Thus storage is
`O(n)` only because `r` and `a` are fixed synchronization-domain constants. If
arbitrarily many origins can be introduced, the honest bound is `O(nr)`.

The bound is independent of operation and synchronization counts, node-value
size/shape/depth, validity-edge count, dependency-proof-map size, and database
age. Origins are stable and are not regenerated by restart, reset, migration,
or active/inactive cutover.

### Goal 3 — algebraic synchronization

**The replicated notification state of the journal synchronizes commutatively,
associatively, and idempotently.** That replicated state is exactly
`NotificationClock`, which joins coordinate-wise by maximum sequence. Local
delivery indices, heads, watermarks, and physical gaps are cursor
infrastructure, not algebraic merge state.

### Non-goal — graph authority

**The graph database is the sole authority for graph state.**

**The journal is not a graph-state source.** It never determines values,
materialization, freshness, validity edges, dependency validity, timestamps,
identifiers, graph conflict winners, graph synchronization results, migration
results, or reset results. There is no journal-to-graph projection.

## Authority and bounded architecture

```text
GraphReplica
├── authoritative IncrementalGraph storage
└── notification journal
    ├── NotificationClock
    ├── DeliveryByIndex
    ├── DeliveryHead
    ├── JournalDomain
    ├── JournalOriginId
    └── lastLocalJournalIndex
```

The journal is physically inside each graph replica. Building an inactive
replica copies the active local replica's journal state exactly, preserving
same-process cursors. Remote physical delivery history is never imported; only
`NotificationClock` is joined between hosts.

## Exact action semantics

`JournalAction = "add" | "edit" | "delete" | "invalidate" | "validate"`.
There is no generic `change` and no broader reading of any action.

- **add** iff absent becomes materialized. It is not a value change and does
  not also report the new node's freshness.
- **edit** iff the node is materialized before and after and its values are
  unequal under normative `ComputedValue` equality.
- **delete** iff materialized becomes absent. It does not also report loss of
  freshness.
- **invalidate** iff a materialized node's authoritative freshness changes
  from up-to-date to potentially-outdated.
- **validate** iff a materialized node's authoritative freshness changes from
  potentially-outdated to up-to-date.

An edit notification exists if and only if a materialized node's
`ComputedValue` changed. Identifier, timestamp-only, validity-relation,
freshness, dependency-metadata, storage-representation, and migration-encoding
changes do not broaden `edit` when the value is equal.

An invalidate notification exists if and only if a materialized node's
freshness sublevel changed from up-to-date to potentially-outdated. Repeated
invalidation, validity/evidence/dependency changes with unchanged freshness,
add, and delete do not emit it.

A validate notification exists if and only if a materialized node's freshness
sublevel changed from potentially-outdated to up-to-date. Work while already
fresh, proof or validity changes, representation changes, add, and delete do
not emit it.

Independent simultaneous transitions produce multiple actions: a value change
plus fresh-to-stale emits `edit` and `invalidate`; a value change plus
stale-to-fresh emits `edit` and `validate`. Add and delete are exclusive
materialization transitions and never additionally produce freshness actions.

## Journal-observable graph surface

The complete surface is exactly materialization presence, `ComputedValue`, and
freshness sublevel. Other fields are derived from those dimensions, cannot
change independently, or are deliberately non-observable internal metadata.
`createdAt` changes only with add; `modifiedAt` only with a value change and
therefore edit; `NodeIdentifier` is stable for a semantic node or identity
replacement is specified as delete plus add; validity edges can change silently
while freshness is unchanged; storage representation is not observable. No
other independently changing semantic field is presently in this contract.

## Core guarantees

The synchronized clock contains one counter/time component per
key/origin/action, while local delivery retains at most one physical record per
key/action. Local transactions atomically mutate authoritative state, advance
their clock coordinates, and append-or-replace delivery records. Synchronization
joins clocks independently from authoritative graph synchronization and adds
local delivery coverage for both remote advances and cutover-created graph
transitions.

Historic deleted keys remain in `n`. The exact size proof, synchronization
algebra, emission rules, cursor proof, migration, and locking protocol are in
the corresponding files under `docs/specs/`.

## Normative invariants

- The graph merge is fully specified independently of the journal.
- The notification clock never chooses graph state.
- The journal rewrite does not remove or weaken the observatory locking model.
- The graph database is the sole authority for graph state.
- The journal is a notification source and never a graph-state source.
- The journal has no false negatives for materialization, `ComputedValue`, or
  freshness-sublevel changes.
- `add` means only absent-to-materialized.
- `edit` means only a `ComputedValue` change while materialized.
- `delete` means only materialized-to-absent.
- `invalidate` means only freshness changed from up-to-date to
  potentially-outdated.
- `validate` means only freshness changed from potentially-outdated to
  up-to-date.
- Notification-clock synchronization is pointwise maximum and is commutative,
  associative, and idempotent.
- Every writable host has one unique origin from a fixed finite synchronization
  domain.
- Unknown origins cannot enlarge a clock.
- For a fixed journal domain, total live journal state is O(n).
- The replicated `NotificationClock` join is commutative, associative, and
  idempotent.
- Local delivery indices are cursor infrastructure and are not part of the
  algebraic merge result.
- Concurrent origins and distinct actions cannot overwrite one another.
- At most one local delivery record exists per historic node key and exact
  action.
- For a fixed synchronization domain, total journal storage is `O(n)`, where
  `n` is the number of current and historic node keys.
- Journal storage is independent of node value size and operation history
  length.
- The journal remains physically inside the graph replica and is copied as
  local cursor infrastructure during replica construction.
- No committed materialization, value, or freshness transition lacks a covering
  notification.

## Strict O(n) proof

Let `n` be the number of current and historic semantic node keys, `r` the fixed
number of origins, and `a = 5`. `NotificationClock` has at most `n × r × a`
components. `DeliveryHead` and `DeliveryByIndex` each have at most `n × a`
entries. `JournalOriginId` and `lastLocalJournalIndex` are constant replica
metadata. Therefore:

```text
journal size = O(nra + na) = O(n)
```

The last equality requires fixed `r` and `a`; with unbounded origins it is
`O(nr)`. Historic deleted keys remain in `n`. Mandatory replacement maintains
the bound continuously. Operation/synchronization count, value/proof size,
graph age, validity edges, and obsolete intermediate values add no terms.
For this protocol version, `allowedOrigins` is finite and immutable, so `r` is
an enforced domain constant. For a fixed journal domain, total live journal
state is O(n).

## No-false-negatives proof

### Local and repeated actions

A local committed transition, clock advancement, and delivery replacement share
one atomic batch, so the transition cannot commit without coverage. Repeated
edits can move sequence 7→8→9; a peer at 7 detects 9. Occurrences may collapse,
but possible edit does not. Separate action coordinates prevent `edit` from
overwriting `invalidate`, and `add` from overwriting `delete`.

### Origins and round trips

Separate origins preserve concurrent writers: seeing origin A earlier does not
hide later discovery of origin B. For absent→present→absent, both add and delete
advance even if a receiving graph stays absent. For A→B→A, edit advances twice
even if final value matches. For fresh→stale→fresh, invalidate and validate both
advance even if final freshness matches.

### Synchronization-created transition

If authoritative synchronization changes local value or freshness without a
matching incoming action advancement, `SyncGraphActions` classifies the local
before/final states and creates the missing local delivery at cutover. Thus the
union of remote advancements and local synchronization transitions covers both
sources of possible change.
